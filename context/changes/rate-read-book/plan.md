# Mark book as read and rate it Implementation Plan

## Overview

A signed-in household member opens a minimal book list and a book detail page and marks the book as read in one form: rating 1-5, read date and an optional comment. The read record (including its comment) is immutable: it can only be removed (hard delete) and created again. Comments are visible to every signed-in user with an obfuscated author e-mail; per-comment privacy is a separate later change. This is roadmap S-03 (FR-008, US-01, FR-009 pulled forward) and it feeds the S-04 recommendation rule with ratings and read dates.

## Current State Analysis

- `Book`, `Author`, `Tag`, `User` exist (`src/Entity/Book.php`, `src/Entity/User.php`). Nothing links a user to a book except `Book::$addedBy`.
- The only book route is `/books/new` (`src/Controller/BookController.php:18`). There is no list, no detail page, and the home page is static (`templates/home/index.html.twig`). S-05 (browse and search) is not built, so S-03 has to bring a plain list and detail page to have somewhere to act.
- Pattern to follow: input DTO with validation + Symfony form type + service wrapping work in `wrapInTransaction` + a thin controller with `#[IsGranted('ROLE_USER')]` and an explicit 400 on invalid forms (`src/Controller/BookController.php:21-40`, `src/Service/BookManager.php:28`). Polish strings live in `translations/messages.pl.yaml` and `translations/validators.pl.yaml`.
- Tests run in a rolled-back transaction per test (`dama/doctrine-test-bundle`), `phpunit.dist.xml` fails on deprecations, notices and warnings. Tests must not run DDL or commit.
- Migrations are generated by `make:migration` and reviewed by hand (`migrations/Version20261103191639.php`); never `doctrine:schema:update`.
- Roadmap question 11 (comments) is open and contradicts the PRD rule that comments are personal (FR-009, Access Control, Guardrails). The owner decided in this planning session: comments are included now as an optional field of the mark-as-read form, one per read record, visible to all signed-in users together with the author's rating (a rating is shown only next to a comment); privacy is a separate change.

## Desired End State

A signed-in user sees all books on `/books`, each with their own read state. On `/books/{id}` they see the book, their own read state, and the comments of all readers. If the book is not marked read they see one form: rating 1-5, read date (default today, not in the future) and an optional comment. After saving they see their rating, date and comment and a "remove my read mark" button. Removing asks for confirmation that it deletes the rating, date and comment, then returns the book to unread. A user sees another reader's rating only next to that reader's comment; comments show the author's rating and an obfuscated e-mail such as `a***@example.com`. Anonymous visitors are redirected to login on every new route. The test suite is green, the migration is applied on production and the flow works there.

Verify by: `php bin/phpunit` green, `doctrine:schema:validate --env=test` clean, and the manual walkthrough in each phase.

### Key Discoveries:

- No list or detail UI exists, so S-03 includes a minimal one (`src/Controller/BookController.php:18`, `templates/home/index.html.twig`).
- `Book` has no soft-delete column yet; S-08 adds `deleted_at`, so `/books` and `/books/{id}` must read books through repository methods that S-08 can later filter (`src/Repository/BookRepository.php`).
- Existing foreign keys to `user` use `ON DELETE RESTRICT` (`migrations/Version20261103191639.php`); the new table follows that so data is never lost silently.
- Authors' full names are `Author::getFirstName()/getLastName()`; the list and detail page show them joined, the same way for both views.

## What We're NOT Doing

- Editing a read record's rating, date or comment (create and remove only).
- Soft delete of read records; removal is a hard delete by the owner's decision.
- Separate comments: no `ReaderComment` entity, no add-comment form, no delete-single-comment action, no multiple comments per user and book (the comment is one optional field of the read record).
- Comment visibility flag, per-comment privacy and any rewrite of the PRD privacy rules beyond the comments relaxation (new roadmap slice S-09).
- Search, filters, pagination or sorting options on `/books` (S-05); the list is a plain list.
- Recommendations and any average rating shown to users (S-04); a rating is visible to others only next to its author's comment.
- Edit and delete of books (S-07, S-08) and duplicate warnings (S-06).
- Showing other users' read dates anywhere, or other users' ratings anywhere except next to their comment in the comments block.
- Real privacy for e-mail addresses: obfuscation (`a***@example.com`) only reduces exposure, it does not make authors anonymous.

## Implementation Approach

Build bottom-up in five commit-sized phases: schema, read-only list and detail, the read/rate/comment flow, shared comments display, then docs and production. A `ReadBook` row (user, book, rating, read date, optional comment) is the single source of truth for "user X read book Y" and for that user's comment, so a user who has not read a book cannot have a comment on it and removing the record removes the comment with no extra code. `ReadingManager` holds the rules; controllers wire form, service and flash, as in S-02. Use TDD with the existing `WebTestCase` and rolled-back transactions.

## Critical Implementation Details

- **Read date.** Store a calendar date (`DATE`, no time), compared with today in the application time zone; reject a date later than today. Because the "last year" rule in S-04 depends on it, name the column `read_on` and keep it a plain date.
- **Duplicate submit.** `(user_id, book_id)` is unique; a second submit (double click, second tab) must end as a friendly "already marked" message, not an unhandled `UniqueConstraintViolationException`.
- **Time zone.** "Today" is the calendar day in `Europe/Warsaw`, not the server's UTC day, so a household member entering today's date shortly after midnight local time is not rejected as future. Phase 3 sets the PHP default time zone to `Europe/Warsaw` (image PHP ini and an `<ini name="date.timezone">` entry in `phpunit.dist.xml`) and tests the boundary with a frozen clock.
- **Comment storage.** An empty or whitespace-only comment is stored as `NULL`, never as an empty string, so "has a comment" is one check (`comment IS NOT NULL`) in the comments query.

## Phase 1: Read-record data model

### Overview

Add the new table and entity with a reviewed migration, nothing user-visible yet.

### Changes Required:

#### 1. ReadBook entity

**File**: `src/Entity/ReadBook.php`

**Intent**: One row per user and book that the user has read; carries the rating, the date it was read and an optional comment. It is the base of the S-04 recommendation inputs.

**Contract**: Table `read_book`; `id`; `user` (many-to-one `User`, not null, `onDelete: RESTRICT`); `book` (many-to-one `Book`, not null, `onDelete: RESTRICT`); `rating` (smallint, 1-5); `readOn` (`date_immutable`); `comment` (text, nullable); `createdAt` (`datetime_immutable`, set in constructor). Unique constraint `UNIQ_READ_BOOK_USER_BOOK` on `(user_id, book_id)`; index on `book_id` for the future average rating. Getters and fluent setters like `Book`.

#### 2. Repository

**File**: `src/Repository/ReadBookRepository.php`

**Intent**: Typed repository wired through `ServiceEntityRepository` like `BookRepository`; query methods arrive in later phases.

**Contract**: Class `ReadBookRepository`, referenced from the `#[ORM\Entity(repositoryClass: ...)]` attribute.

#### 3. Migration

**File**: `migrations/Version<timestamp>.php`

**Intent**: Create `read_book` with the constraints above; generated by `bin/console make:migration --no-interaction` and then reviewed by hand.

**Contract**: Foreign keys `read_book.user_id -> user.id` and `read_book.book_id -> book.id` with `ON DELETE RESTRICT`; `down()` drops `read_book`. No `CHECK` on rating (validated in the application; the rest of the schema does not use CHECK constraints).

#### 4. Mapping tests

**File**: `tests/Entity/ReadBookMappingTest.php`

**Intent**: Prove the mapping and the constraints behave as designed, in the style of `tests/Entity/BookMappingTest.php`.

**Contract**: Tests: persists and reloads a `ReadBook` with date, rating and comment (and with a null comment); a second row for the same user and book fails with `UniqueConstraintViolationException`; removing a `Book` or `User` that still has a `ReadBook` is rejected.

## Phase 3: Mark as read with rating, date and comment

### Overview

Let a user create a read record with rating, date and optional comment from the detail page, and remove it again.

### Changes Required:

#### 1. Input DTO and form

**File**: `src/Dto/MarkRead.php`, `src/Form/MarkReadType.php`

**Intent**: Validate rating, date and comment before the service runs, with Polish error messages; the comment is a field of the same form as the rating.

**Contract**: `MarkRead` has `?int $rating` (`NotNull`, `Range(min: 1, max: 5)`), `?DateTimeImmutable $readOn` (`NotNull`, `LessThanOrEqual('today')`) and `?string $comment` (optional, `Length(max: 2000)`). `MarkReadType`: rating as expanded `ChoiceType` (radio buttons 1-5), read date as `DateType` with a single text widget in HTML5 mode defaulting to today, comment as `TextareaType` (not required); labels from translations. Validation messages go to `translations/validators.pl.yaml`.

#### 2. ReadingManager service

**File**: `src/Service/ReadingManager.php`

**Intent**: The rules for creating and removing a read record, kept out of the controller.

**Contract**: `markRead(User $user, Book $book, MarkRead $input): ReadBook` creates the record in `wrapInTransaction`, storing the trimmed comment or `NULL` when empty; if one already exists for the pair (checked first, and via a caught unique-constraint violation for the race) it throws `App\Exception\AlreadyReadException`. `remove(User $user, Book $book): void` hard-deletes the user's record for that book (rating, date and comment together) and returns quietly when none exists. Neither method takes a second user, so one user can never touch another's record.

#### 3. Controller actions

**File**: `src/Controller/ReadBookController.php`

**Intent**: Two POST routes that act on the current user's own record only.

**Contract**: `POST /books/{id}/read` -> `book_read` (form submit; on invalid input re-render `book/show.html.twig` with an explicit 400 like `new`; on success flash and redirect to `book_show`; `AlreadyReadException` -> warning flash and redirect). `POST /books/{id}/read/remove` -> `book_read_remove` (CSRF token checked, then `ReadingManager::remove`, flash, redirect). Both `#[IsGranted('ROLE_USER')]`; unknown book id -> 404.

#### 4. Detail page read state

**File**: `templates/book/show.html.twig`, `translations/messages.pl.yaml`

**Intent**: Show the form when the book is unread; show the user's own rating, date and comment plus a "remove my read mark" button when it is read. The remove button uses a confirmation stating it deletes the rating, the date and the comment.

**Contract**: Translation keys under `reading.*`. Outside the comments block only the current user's own rating is rendered.

#### 5. Tests

**File**: `tests/Service/ReadingManagerTest.php`, `tests/Controller/ReadBookControllerTest.php`

**Intent**: Prove the rules and the privacy guardrail.

**Contract**: Valid submit stores rating, date, comment and user; a blank comment is stored as `NULL`; a 2001-character comment is rejected; ratings 0, 6 and empty, a future date and a missing date are rejected with 400 and nothing is saved; a date of today is accepted, including just after local midnight with a frozen clock (the UTC day is still yesterday); a second submit for the same book gives the warning and keeps one row; remove deletes the row including its comment; user A's rating never appears on user B's list, nor on B's detail page except next to A's comment; user B's remove request only affects user B's own record; anonymous is redirected to login; a missing or invalid CSRF token on remove is rejected.

### Success Criteria:

#### Automated Verification:

- Tests pass: `php bin/phpunit`
- Schema stays clean: `php bin/console doctrine:schema:validate --env=test`
- Container lints: `php bin/console lint:container`
- Routes registered: `php bin/console debug:router book_read book_read_remove`

#### Manual Verification:

- Marking a book with rating 4, today's date and a comment shows "Przeczytana", rating 4, the date and the comment on the detail page, and the rating on the list
- Marking a book with no comment works and shows no comment
- A back-dated read date is accepted; tomorrow's date shows a Polish error and saves nothing
- Rating 0 or 6 cannot be submitted from the radio buttons and is rejected if forced
- Removing the mark (after the confirmation) returns the book to unread and the form reappears; marking again with a different rating and comment works
- A second user signed in on another browser does not see the first user's rating anywhere except next to the first user's comment (Phase 4)

## Phase 4: Shared reader comments

### Overview

Show every reader's comment on the book detail page to all signed-in users, each with the author's rating and the author's e-mail obfuscated.

### Changes Required:

#### 1. E-mail masking helper

**File**: `src/Service/EmailMasker.php`, `src/Twig/EmailMaskExtension.php`

**Intent**: Single place that turns an e-mail into the form shown next to a comment, so no template prints a raw e-mail.

**Contract**: `mask(string $email): string` keeps the first character of the local part, replaces the rest of the local part with `***`, keeps the domain: `anna@example.com` -> `a***@example.com`; a one-character local part gives `*@example.com`. Exposed as the Twig filter `mask_email`.

#### 2. Comments query

**File**: `src/Repository/ReadBookRepository.php`

**Intent**: Load the comments of one book in a single query.

**Contract**: `findCommentsForBook(Book $book, User $viewer): list<ReadBook>` returns the read records of that book whose `comment IS NOT NULL`, excluding the viewer's own record (it is already shown in their read state), newest first, with `user` fetch-joined. The comments block renders the masked e-mail, the author's rating (1-5) and the comment text; the read date is not shown. A rating is exposed only for records that have a comment.

#### 3. Comments on the detail page

**File**: `templates/book/show.html.twig`, `translations/messages.pl.yaml`

**Intent**: A "Komentarze czytelników" block listing each comment with the masked author e-mail, the author's rating (e.g. "4/5") and the comment text (escaped by Twig, line breaks preserved); an empty-state message when there are none. Visible to every signed-in user (including readers and non-readers); anonymous users never reach the page.

**Contract**: Translation keys under `comments.*`; no delete or edit controls (comments disappear only when their author removes the read record).

#### 4. Tests

**File**: `tests/Service/EmailMaskerTest.php`, `tests/Controller/BookCommentsTest.php`

**Intent**: Prove the masking and the visibility.

**Contract**: Masking examples above plus a one-character local part; user A's comment shows for user B (who has not read the book) with a masked e-mail and no raw e-mail anywhere in the HTML; user A's rating appears next to A's comment in the block, the read date does not; the rating of a read record without a comment appears nowhere for B; records without a comment are not listed; the viewer's own comment is not repeated in the block; comment text containing HTML is shown escaped; removing the read record removes the comment from the page; anonymous gets a redirect to login.

### Success Criteria:

#### Automated Verification:

- Tests pass: `php bin/phpunit`
- Container lints: `php bin/console lint:container`
- Twig lints: `php bin/console lint:twig templates`

#### Manual Verification:

- A second user sees the first user's comment as `a***@example.com`-style text, never the full address, together with the first user's rating next to it
- A comment containing a script tag is displayed as text
- A read record with no comment adds nothing to the block; with no comments at all the empty-state message shows
- After the author removes their read mark, their comment disappears from the other user's view

## Testing Strategy

### Unit Tests:

- `EmailMasker` examples including one-character local part.
- `ReadingManager`: create, duplicate, remove, remove-when-absent, blank comment stored as `NULL`.
- Validation: rating 0/6/empty, future date, today accepted, 2001-character comment.

### Integration Tests:

- `WebTestCase` flows for every new route: anonymous redirect, signed-in success, invalid input -> 400, CSRF failure, 404 paths.
- Privacy: another user's rating appears only next to that user's comment on the detail page and never in the list; no raw e-mail appears next to comments.
- Query count on `/books` stays constant as books grow.

### Manual Testing Steps:

1. Sign in as two users in two browsers; the first marks a book read with rating 4, a back-dated read date and a comment.
2. The second sees the comment with a masked e-mail and the first user's rating, and can mark the same book read with their own rating independently.
3. The first removes the read mark: rating, date and comment disappear; the second user's record stays.
4. Double-click the submit button and submit from two tabs: one row, one friendly message.

## Performance Considerations

The household is 2-4 users with a small collection. The list loads books with authors and the user's read records in a constant number of queries; the comments block is one query per detail page; no pagination in this slice (S-05 owns that).

## Migration Notes

The migration only creates one new table, so existing data is untouched. It runs through the `release_command` in `fly.toml` on deploy; migrations do not roll back on production, so take a database dump before merging if the backup task (roadmap question 10) is still open. `down()` exists for local use.
